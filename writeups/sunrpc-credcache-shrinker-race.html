Linux kernel sunrpc / auth_gss race condition Submitted upstream, under review

A NULL pointer in the SUNRPC cred shrinker

A one-line store without a lock, a memory shrinker running at the wrong moment, and a kernel oops in kswapd at address 0xc.

The symptom

On a kernel running Kerberos-secured NFS, kswapd0 crashed with a page fault on a tiny address:

BUG: unable to handle page fault for address: 000000000000000c
#PF: supervisor write access in kernel mode
RIP: 0010:_raw_spin_lock+0x13/0x60
Call Trace:
 rpcauth_unhash_cred+0x45/0x90 [sunrpc]
 rpcauth_cache_do_shrink+0xb0/0x1e0 [sunrpc]
 rpcauth_cache_shrink_scan+0x34/0x50 [sunrpc]
 do_shrink_slab
 shrink_slab
 shrink_node
 balance_pgdat
 kswapd
Comm: kswapd0   6.8.0-111-generic

An oops at 0xc almost always means "NULL plus a small struct offset". Here 0xc is offsetof(struct rpc_cred_cache, lock). Something was taking a spinlock inside a struct rpc_cred_cache that was NULL.

Where the NULL comes from

Each GSS authenticator (struct rpc_auth) owns a credential cache, reachable through auth->au_credcache. When an auth is destroyed, rpcauth_destroy_credcache() does this:

auth->au_credcache = NULL;        /* no lock held */
rpcauth_clear_credcache(cache);   /* takes rpc_credcache_lock */

The pointer is cleared before the global rpc_credcache_lock is taken to unhash the auth's credentials. For a short window, credentials that belong to the auth being destroyed are still sitting on the global cred_unused LRU list, still flagged RPCAUTH_CRED_HASHED, while their auth already points at no cache.

The memory shrinker walks exactly that list.

The shrinker (rpcauth_cache_shrink_scan(), or rpcauth_cache_enforce_limit() on the lookup path) takes rpc_credcache_lock, walks cred_unused in rpcauth_prune_expired(), and reaches rpcauth_unhash_cred(). That function tested the HASHED bit, found it set, and then did this:

cache_lock = &cred->cr_auth->au_credcache->lock;   /* au_credcache is NULL */
spin_lock(cache_lock);                               /* oops at 0xc */

Is NULL always the teardown?

Before adding a NULL check, it is worth proving that NULL can only mean one thing. A silent early return would be wrong if there were another way to see it.

  • rpcauth_destroy_credcache() is only called from auth_gss.
  • Every GSS credential takes a reference on its gss_auth when it is created.
  • gss_destroy() calls rpcauth_destroy_credcache() before gss_put_auth().

So while a credential is alive, its cr_auth is alive too, and reading NULL from au_credcache can only be that one store. A vmcore from the reproduction confirmed it: cr_auth was the auth being destroyed, au_credcache was 0, the credential had RPCAUTH_CRED_HASHED set with cr_count of 1, and the cache object itself was still allocated.

Reproducing it on demand

The window is tiny in production, so two changes make it reliable:

  1. Lower the auth_max_cred_cachesize module parameter. It defaults to ULONG_MAX, which is effectively no bound.
  2. Add an msleep(200) between the store and rpcauth_clear_credcache(), and run the shrinker (drop_caches) inside that window.

The fix

Treat a cleared cache as "this auth is being torn down" and leave the credential alone. rpcauth_clear_credcache() will unhash it and drop the hash table's reference, so nothing leaks.

static bool
rpcauth_unhash_cred(struct rpc_cred *cred)
{
-    spinlock_t *cache_lock;
+    struct rpc_cred_cache *cache;
     bool ret;

     if (!test_bit(RPCAUTH_CRED_HASHED, &cred->cr_flags))
         return false;
-    cache_lock = &cred->cr_auth->au_credcache->lock;
-    spin_lock(cache_lock);
+    cache = READ_ONCE(cred->cr_auth->au_credcache);
+    if (!cache)
+        return false;
+    spin_lock(&cache->lock);
     ret = rpcauth_unhash_cred_locked(cred);
-    spin_unlock(cache_lock);
+    spin_unlock(&cache->lock);
     return ret;
 }

 /* in rpcauth_destroy_credcache() */
-        auth->au_credcache = NULL;
+        WRITE_ONCE(auth->au_credcache, NULL);
  • One read. The old code dereferenced au_credcache in the middle of an expression. The new code reads it once into a local, so the NULL test and the lock use the same value.
  • READ_ONCE / WRITE_ONCE. The store is made without the lock and the load happens under a different one, so the compiler must not tear, fuse, or re-read either access. These annotations say so explicitly.
  • Lock ordering is unchanged. It is still rpc_credcache_lock, then cache->lock.

Takeaway. A pointer that is published as NULL without a lock is only safe if every reader treats NULL as a valid state. The fix is not a new lock. It is making the reader handle the state the writer already creates.
