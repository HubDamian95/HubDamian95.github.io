One uninitialized field, one wrong RDMA chunk

Why a large NFS read over RDMA sometimes went out the slow way, and why it only happened sometimes.

The symptom

Over RPC/RDMA, a large READ on plain krb5 was sometimes sent with a reply chunk instead of a write chunk, even though a write chunk was all it needed. Same mount, same flavor, different behavior from one client run to another. Non-deterministic behavior of that kind usually points at uninitialized memory.

Why it mattered

rpcrdma_marshal_req() looks at a bit in the auth flags, RPCAUTH_AUTH_DATATOUCH, and reads it as "this GSS flavor must not place payload bytes directly". For integrity and privacy flavors (krb5i, krb5p) that is true, because the payload has to be checksummed or encrypted, so the data cannot be written straight into the application buffer. For plain krb5 it is false, and the read should use a write chunk.

Where the bit came from

gss_create_new() gets its struct gss_auth from kmalloc(), which does not zero memory, and then sets flags only with __set_bit():

  • RPCAUTH_AUTH_UPDATE_SLACK is set on every GSS auth.
  • RPCAUTH_AUTH_DATATOUCH is set only for krb5i and krb5p.

__set_bit() only turns a bit on and leaves every other bit alone. Nothing ever stored a clean value into au_flags. So whatever the slab allocator handed back, bit for bit, was the starting state.

If that memory previously held a structure whose DATATOUCH bit position was set, a plain krb5 auth inherited it, on kernels that do not zero allocations. Whether it happened depended on what had lived at that address before.

The fix

     auth->au_rslack = GSS_KRB5_MAX_SLACK_NEEDED >> 2;
     auth->au_verfsize = GSS_VERF_SLACK >> 2;
     auth->au_ralign = GSS_VERF_SLACK >> 2;
+    auth->au_flags = 0;
     __set_bit(RPCAUTH_AUTH_UPDATE_SLACK, &auth->au_flags);

One line. The alternative was to switch the allocation to kzalloc(), which would zero the whole struct. The patch instead initializes the field explicitly, to stay aligned with how the surrounding fields are already initialized one by one.

Lessons

  • Bit helpers are not initializers. __set_bit() and set_bit() assume the word already has a defined value.
  • "Sometimes" is a clue. A flag that depends on flavor but misbehaves intermittently on one flavor looks like state the code never set, not logic it set wrongly.
  • The consumer can be far from the bug. The wrong value was written in auth_gss and only became visible as a different chunk choice in the RDMA transport.
