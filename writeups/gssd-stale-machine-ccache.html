gssd said "good until" while every upcall failed

A daemon that trusts its memory of the last time it did something, instead of looking at the thing itself, will eventually lie confidently. This is one of those bugs.

The symptom

On a Kerberos-secured NFS client, machine-credential upcalls started failing for hours. The kernel received -EACCES (err -13) on every downcall. Meanwhile rpc.gssd kept logging, right before each failure:

Credentials in CC 'FILE:...' are good until <a time 10 hours ahead>
Failed to create machine krb5 context

The log said the credentials were fine, and the next line said they were not.

How the cache check worked

gssd_get_single_krb5_cred() decides whether it needs to run kinit from the keytab. It skipped the kinit while two things were true:

  1. ple->endtime, the endtime of gssd's own last kinit, was more than five minutes away, and
  2. the machine ccache file existed.

Nothing ever read the file again. Existence and modification time say nothing about what is inside it.

The failure mode. Another writer replaces the machine ccache with a different ticket, and that ticket later expires. gssd's remembered endtime still looks healthy, the file still exists, and gssd keeps returning success for a credential it never re-examined.

In the environment where this surfaced, a separate service kept the machine ccache fresh by atomically replacing the file. When that service's ticket expired, gssd had no way to notice.

What actually matters in a ccache

A file ccache is a list of tickets. libkrb5 appends every new service ticket to the selected ccache, so a cache can be full of service tickets and still be useless. Only the TGT (ticket-granting ticket) can obtain a ticket for a server that is not already in the file. If the TGT is gone or expired, nothing new can be fetched.

The fix: read the cache every time

For the file ccache, gssd now reads it on every call. The cache is accepted only if all of this holds:

  • its default principal equals ple->princ (GSS-API initiates as that name),
  • it holds a krbtgt/REALM@REALM ticket,
  • that ticket was issued to ple->princ,
  • it has already started, and is not flagged invalid (postdated),
  • it is valid for at least another five minutes, which is the existing clock-skew margin.

If so, gssd uses it. Otherwise it runs kinit from the keytab exactly as before. The memcache path is unchanged, and so is the "good until" log text, which now reports the endtime of the TGT actually found in the file.

A race hiding inside the check

Each krb5_cc_* call on a FILE ccache reopens the file. If something renames a new file into place between krb5_cc_get_principal() and the scan for the TGT, the code could pair the old file's principal with the new file's TGT, and approve a cache that was never consistent.

So the TGT's client is verified in the same scan that finds the TGT, which reads from one open file. The default principal is still compared as well.

Why no lock

Replacing a file with rename(2) is atomic, so a reader sees either the whole old file or the whole new one. A read that races gssd's own kinit just fails the check and falls into the existing locked kinit path. There is no state to protect.

As a side effect, where an external refresher keeps the file valid, gssd now never runs kinit, so it no longer fights that refresher over the file.

A second bug: the retry that retried nothing

While in krb5_use_machine_creds(), the same patch fixes a literal 0 passed where the retry flag belonged:

gssd_refresh_krb5_machine_credential(clp->servername,
-                     service, srchost, 0);
+                     service, srchost, nocache);

The code path logs "Machine cache prematurely expired or corrupted trying to recreate cache" and retries, but because it passed 0 every time, the retry repeated the first attempt with identical arguments. It now skips the ccache check and runs kinit from the keytab, which is what a retry should do.

Takeaway. Cache invalidation by "I remember when I last wrote it" breaks as soon as anyone else may write. Re-validate against the real object, and make sure every field you compare comes from the same read.
